PROJECT APPROACH (PROPOSED, TO FINALIZE IN BLOCK A)
Retain healthcare as the application domain unless the user changes it,
while designing and implementing the final jury project independently.
Choose a public, documented dataset with a meaningful classification target
and useful numeric features for interpretable clustering. Confirm its
warehouse, mining, and learning suitability before locking the design.

Use one new local dashboard with A-J navigation in rubric order, independent
SQL/ETL scripts, and reproducible training/mining scripts. Proposed tools:
Python, Streamlit, pandas, scikit-learn, mlxtend, and Snowflake. Finalize
versions and dataset-specific choices during implementation.

Every block is complete only when its required content works, its saved
results can be traced to a run, and its explanation can be given orally.
Record actual results only; the plan contains no performance claims.

BLOCK A - DASHBOARD 1: DATA WAREHOUSE DESIGN | 3 MARKS | PDF PAGES 1-2
Build:
- Define the application domain, business problem, and analytical questions.
- Select and independently acquire documented source data; record source,
  license/access terms, original shape, column dictionary, and limitations.
- Declare the fact-table grain before deciding facts and dimensions.
- Design a suitable star or snowflake schema with keys, relationships,
  cardinality, and justified measures. Do not invent unavailable fields.
- Implement and show the warehouse structure; prepare reproducible DDL and
  an ETL mapping ready for deployment in Block B.
Save: problem statement, source manifest, schema diagram, data dictionary,
      DDL, transformation mapping, and Block A evidence.
Done when: the business questions map to real fields and the fact grain,
           joins, measures, and schema can be explained and demonstrated.

BLOCK B - DASHBOARD 2: SNOWFLAKE DEPLOYMENT | 3 MARKS | PDF PAGE 2
Build:
- Demonstrate a real Snowflake environment and its compute/storage roles.
- Create a dedicated final jury database and schema, then the Block A tables.
- Load this project's data and reconcile source, accepted, and loaded counts.
- Run meaningful SQL joins and aggregations on the uploaded data.
- Show how the deployed tables correspond to the Block A schema.
Save: setup/load/query SQL, count and join checks, query outputs, and real
      Snowflake screenshots. Keep credentials out of saved evidence.
Done when: the actual Snowflake tables contain verified data and queries run.
Dependency: an accessible Snowflake account with suitable create/load/query
            permissions. Check access during Block A to avoid a late delay.
            Prepared SQL alone does not complete this deployment criterion.

BLOCK C - DASHBOARD 3: SUPERVISED DATASET | 1 MARK | PDF PAGES 2-3
Build:
- Show the dataset name/source, record count, and attribute count.
- Identify input features, target classes, and the intended application.
- Show missingness, class balance, and any filtering/exclusions.
- Define a leakage-safe split before fitting transformations. Keep repeated
  entities together where applicable; remove identifiers and target proxies.
Save: dataset card, feature/target specification, prepared-data preview,
      split manifest, and dataset evidence.
Done when: the learning task and each feature's availability are defensible.

BLOCK D - APRIORI AND FP-GROWTH | 1 MARK | PDF PAGE 3
Build:
- Explain frequent itemsets and prepare justified transactions/items.
- Run both Apriori and FP-Growth on the same transactions and thresholds.
- Show actual itemsets/rules with support, confidence, and lift.
- Interpret useful rules, including whether a rule adds meaningful insight.
Save: transaction recipe, parameters, itemsets, rules, and evidence.
Done when: both algorithms run and at least representative rule calculations
           and interpretations can be explained. Document sparse/no-rule
           results honestly and adjust only with a stated rationale.

BLOCK E - CLASSIFICATION COMPARISON AND VALIDATION | 2 MARKS | PDF PAGE 3
Build:
- Train one primary classifier and at least two other suitable classifiers.
- Initial candidates: Random Forest, Logistic Regression, Decision Tree;
  finalize suitability against Block C's data rather than assume a winner.
- Use the same held-out split and training-only fitted preprocessing.
- Use training/validation data for model and parameter selection; keep the
  final test set out of that selection. Add a majority-class baseline.
- Present comparative results and explain tradeoffs and validation choices.
Save: fitted pipelines, parameters/seeds, split references, comparison table,
      validation method, and measured results.
Done when: comparison is reproducible and fair, and a model choice is justified.
Order note: E explicitly requires implementation of the primary classifier.
            Train it here; F then demonstrates that implementation in depth.

BLOCK F - CLASSIFICATION IMPLEMENTATION | 2 MARKS | PDF PAGES 3-4
Build:
- Explain the selected classifier and its preprocessing step by step.
- Demonstrate training and real predictions using the Block E pipeline.
- Explain predicted classes and classification decisions; distinguish model

Save: model explanation, preprocessing/training walkthrough, example inputs
      and predictions, and demonstration evidence.
Done when: a sample travels from input through preprocessing to prediction,

BLOCK G - UNSUPERVISED DATASET | 5 MARKS | PDF PAGE 4
Build:
- Document dataset name/source, records, attributes, and characteristics.
- Select and justify clustering features, excluding identifiers and labels
  from distance/model inputs. Explain encoding and feature weighting.
- Handle missing data and scaling; show the prepared clustering matrix.
- Explain why the dataset supports useful similarity-based segmentation.
Save: dataset card, feature selection rationale, preprocessing pipeline,
      before/after data preview, and clustering input manifest.
Done when: the selected features, representation, and clustering purpose
           are clear and the input is reproducible.

BLOCK H - FOUR CLUSTERING ALGORITHMS | 10 MARKS | PDF PAGES 4-5
Build:
- Proposed four: K-Means, Agglomerative Hierarchical Clustering, DBSCAN,
  and Gaussian Mixture Model. These satisfy the minimum; K-Medoids is optional.
- Explain each algorithm's principle, assumptions, parameters, strengths,
  and limitations. Use the same prepared feature representation and records.
- If runtime requires a sample, select and document one fixed sample for all
  four methods; show its relationship to the full dataset.
- Run a bounded, recorded parameter exploration; show actual cluster sizes,
  noise where applicable, runtime, profiles, and consistent visualizations.
- Use PCA only for display unless a separate modeling choice is justified.
- Compare silhouette, Davies-Bouldin, and Calinski-Harabasz where defined.
  For DBSCAN, disclose noise coverage and how noise enters each calculation;
  do not compare scores on differing retained subsets without explanation.
- Choose the most suitable result using separation, coverage, stability or
  sensitivity evidence, interpretability, and practical usefulness.
Save: four runs, parameters, assignments, comparison table, plots, profiles,
      limitations, and a reasoned selection.
Done when: all four implementations work and the choice follows evidence.

BLOCK I - SELECTED CLUSTERING IMPLEMENTATION | 5 MARKS | PDF PAGE 5
Build:
- Explain the method selected in H and demonstrate its implementation.
- Justify parameters and show the resulting clusters and representative cases.
- Interpret practical meaning from observed cluster profiles; acknowledge
  weak separation or instability and avoid unsupported clinical labels.
Save: algorithm walkthrough, parameter rationale, detailed profiles,
      visualizations, practical interpretation, and demo evidence.
Done when: cluster formation and its practical significance can be explained.

BLOCK J - PERFORMANCE METRICS | 5 MARKS | PDF PAGES 5-6
Build:
- Present accuracy, precision, recall, F1-score, and confusion matrix.
- State class order and averaging; include per-class results and suitable
  aggregate scores so imbalance is visible. Explain mistakes and tradeoffs.
- Consolidate and interpret H's clustering evaluation as supporting analysis;
  report undefined metrics as undefined with a reason.
Save: final metrics tables, labeled confusion matrices, clustering evaluation,
      and a plain-language interpretation of strengths and limitations.
Done when: reported values match saved predictions/assignments and the user
           can explain what each metric measures and what it misses.
