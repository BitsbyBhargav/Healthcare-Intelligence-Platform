PROJECT APPROACH (PROPOSED, TO FINALIZE IN BLOCK A)
Advance the existing healthcare/readmission project rather than replace it
with a different domain or unrelated hospital business problem. Retain the
original raw diabetes encounter data as the foundation and evaluate similar
additional sources. Implement the final jury work separately.

Faculty feedback relayed by the user: increase dataset volume, integrate
similar data, and develop a new business solution from that expanded base.
Proposed extension: readmission risk segmentation and follow-up planning,
with hospital resource analysis supported by actual available fields. This
is an academic decision-support prototype; no reduction in readmissions or
clinical effectiveness is claimed.

Do not append duplicate mirrors of the UCI dataset as new encounters. Do not
join unrelated people across sources using similar demographics or colliding
IDs. Retain source-specific keys, units, outcome definitions, and provenance.
Different-source data need a justified common schema and compatibility checks.
Keep synthetic data explicitly separate in provenance and evaluation if it
is approved. Count unique encounters separately from other warehouse rows.
Missing readmission labels must not be invented. Added hospital activity
data can support operations analysis without becoming labeled readmission
training examples. Confirm warehouse, mining, classification, and clustering
suitability before locking the schema.

Use one new local dashboard with A-J navigation in rubric order, independent
SQL/ETL scripts, and reproducible training/mining scripts. Proposed tools:
Python, Streamlit, pandas, scikit-learn, mlxtend, and Snowflake. Finalize
versions and dataset-specific choices during implementation.

Every block is complete only when its required content works, its saved
results can be traced to a run, and its explanation can be given orally.
Record actual results only; the plan contains no performance claims.

BLOCK H - FOUR CLUSTERING ALGORITHMS | 10 MARKS | PDF PAGES 4-5
Build:
- Proposed four: K-Means, Agglomerative Hierarchical Clustering, DBSCAN,
  and Gaussian Mixture Model. These satisfy the minimum; K-Medoids is optional.
- Explain each algorithm's principle, assumptions, parameters, strengths,
  and limitations. Use the same prepared feature representation and records.
- If runtime requires a sample, select and document one fixed sample for all
  four methods; show its relationship to the full dataset.
- Run a bounded, recorded parameter exploration; show actual cluster sizes,
  noise where applicable, runtime, profiles, and consistent visualizations.
- Use PCA only for display unless a separate modeling choice is justified.
- Compare silhouette, Davies-Bouldin, and Calinski-Harabasz where defined.
  For DBSCAN, disclose noise coverage and how noise enters each calculation;
  do not compare scores on differing retained subsets without explanation.
- Choose the most suitable result using separation, coverage, stability or
  sensitivity evidence, interpretability, and practical usefulness.
Save: four runs, parameters, assignments, comparison table, plots, profiles,
      limitations, and a reasoned selection.
Done when: all four implementations work and the choice follows evidence.
